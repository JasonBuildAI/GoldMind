# 消息板块落库修复：url 列宽与逐行落库

> 状态标记：**现状**（2026-10-02 修复并落地）。本文是这一轮的规约记录；
> 落地后的唯一权威来源是 `README.md` 与 `docs/`（实现口径见 `docs/ARCHITECTURE.md` 第十二节）。

## 一、需求段（做什么、为什么、怎么算做完）

### 背景与问题

消息板块上线当天，手动「抓取最新消息」的报告是「13/13 源成功、110 条重复、0 新增」，
页面却始终显示「尚未抓取过消息」—— 三个窗口全空。MySQL 日志里的根因：

    (pymysql.err.DataError) (1406, "Data too long for column 'url' at row 1")

Google News 的文章链接实测最长 517 字符，超过 `news_digest_items.url` 的
`VARCHAR(500)`。MySQL 拒绝整批 INSERT 并整体回滚；SQLite（测试与 CI 的口径）
不校验长度 —— 905 条测试全绿，只有真实部署落不了库。更糟的是 `_save_items`
把「落库失败」折叠成 `new_items=0`，在报告里与「全部重复」无法区分，故障因此静默。

### 做什么

1. `news_digest_items.url` 由 `VARCHAR(500)` 改为 `TEXT`（去重仍走前缀索引 191）。
2. 落库改为逐行 savepoint：一行出错只跳过该行，不再拖垮整批；跳过的行数如实计入
   抓取报告 `skipped_unstorable` 与日志，`duplicates` 不再把跳过的行算作重复。
3. 既有 MySQL 库用迁移脚本升级：`backend/scripts/migrate_news_digest_url.py`
   （默认 dry-run；`--apply` 执行；`--rollback` 在存在超长行时拒绝，不截断数据）。
4. 前端抓取报告在 `skipped_unstorable > 0` 时显示对应计数。

### 判据（一条会红的测试或一条能跑证明的命令）

- 单测：MySQL 方言下 `url` 列编译为 `TEXT`（改回 VARCHAR 必红）；`schema.sql` 同步；
  一行 NOT NULL 违反时其余行照常入库且 `skipped_unstorable=1`；
  迁移脚本各分支（升级 / 已是 TEXT / SQLite 直通 / 表缺失 / 回滚守卫）。
- 能跑证明：对真实 MySQL 跑迁移 → `POST /api/gold/news/digest/refresh` →
  `GET /api/gold/news/digest` 三个窗口非空。
- 闸门全绿（命令的唯一真源是 `README.md` 的「常用命令」）。

### 明确不做

- 不动 `gold_news.url`（既有分析链路，另案评估）。
- 不改评分、排序、来源池与窗口口径；不删任何既有数据。

### 怎么回滚

- 代码：revert 本提交。
- 库：`python scripts/migrate_news_digest_url.py --rollback`；库里存在超过 500 字符的行时
  脚本拒绝执行并打印行数，绝不截断数据。

## 二、方案段

- 模型与 `schema.sql`：`url` 列类型改为 `Text`；`ix_news_digest_items_url` 保留
  `mysql_length=191` 前缀（TEXT 在 MySQL 下同样需要前缀索引）。
- 服务：`_save_items` 返回 `(inserted, skipped)`；每行一个 SAVEPOINT
  （`db.begin_nested()`），失败记 warning 后继续；外层 commit 失败时把已插行数
  一并计入 skipped —— 宁可报「没落上」，也不报成「重复」。
- 报告：`DigestFetchReport` 增加 `skipped_unstorable`（默认 0，旧缓存报告仍可解析）。
- 迁移：`plan_for(dialect, table_exists, current_type)` 与
  `rollback_for(dialect, current_type, max_url_chars)` 为纯函数，测试不依赖 MySQL；
  脚本对 SQLite 直通（SQLite 不强制 VARCHAR 长度）。
