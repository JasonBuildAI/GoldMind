# 失败率治理：让「整页失败」不再发生

> 本轮改动的 spec。需求段只讲做什么、为什么、怎么算做完；技术从「方案段」开始。
> 落地后的结论以 `README.md`、`docs/ARCHITECTURE.md` 为准；本文件只是这一轮的记录。

- 日期：2026-10-02
- 上游：`docs/specs/2026-10-02-量化策略提升路线图.md`（本轮不改量化口径）
- 状态：现状（2026-10-02 落地）

---

## 一、需求段

### 改什么

用户报告：几乎每一块地方都容易「分析 / 抓取失败」，**有时刷新一下就好**。

实测定位出两类互不相同的原因：

1. **数据库缺表 / 缺数据（持久性）**：开发库 `gold_analysis` 只剩一张空的
   `update_logs`，所有读库接口（stats / prices / quant / news / institutions）
   一律 500，页面整片「暂不可用」—— 刷新永远不会好。
2. **限流 + 无重试（间歇性）**：一个打开的看板每 10 秒对 stats / daily /
   correlation / dollar-realtime 各拉一次（24 次/分钟），加上首屏约 15 个区块请求
   （开发态 StrictMode 再×2），首分钟就逼近普通接口 60 次/分钟的上限；
   触发 429 后，前端只对「无响应」类错误重试，429 / 5xx 直接判失败 ——
   于是整片报错，过一会儿刷新又好。

### 判据

- 开发库重建后，`/api/gold/{stats,prices/daily,prices/correlation,quant/*,news,institutions}`
  全部 200（命令输出为准）；
- 缺表时读库接口返回 **503 + 说明 + 修复命令**，而不是裸 500；
- 429 / 5xx / 网络错误会被有限次退避重试（尊重 `Retry-After`），POST 永不重试；
- 看板轮询从 10s 放宽到 30s，页面隐藏时暂停 —— 空闲请求量 ≤ 8 次/分钟；
- 新增守卫测试全绿；中英 README 与 CHANGELOG 同步。

### 明确不做

- 不改量化引擎口径与预注册（另一份 spec 的范围）；
- 不动数据源抓取逻辑（抓不到时的「不可用 + 原因」是正确行为）；
- 不引入后端重试队列等新机制（重试是客户端行为）。

### 怎么回滚

- 代码：`git revert` 对应 commit；
- 数据：`init_db.py` 与回填脚本可重跑；`.env` 不动。

## 二、方案段

1. **数据**：用仓库自带脚本重建（`init_db.py` → `backfill_quant.py --apply --years 20`）。
2. **后端**：全局异常处理器把「表不存在」（SQLAlchemy `ProgrammingError`，MySQL 1146）
   翻译成 503 + `detail`（含 `python init_db.py` 修复指引）；应用启动时做一次
   schema 探针，缺表打 ERROR 日志并给出同一句指引；两者都不吞错、不改其它错误语义。
3. **前端**：
   - `api.ts`：重试扩展到网络错误、超时、429、5xx；指数退避 + 抖动，429 优先按
     `Retry-After` / `retry_after` 等待；上限 3 次；POST 仍不重试（付费调用语义不变）;
   - `GoldDataContext`：轮询 10s → 30s；`document.hidden` 时暂停、恢复时立即补一次；
     同一 URL 在飞请求去重（single-flight）。
4. **文档**：README（中英）排障新增「整片暂不可用」；`ARCHITECTURE.md` 补失败传播与
   重试口径；CHANGELOG `[Unreleased]` 一行一条。

## 三、落地结果

全部按上表落地，2026-10-02 19:00 前后逐项实测。

### 1. 根因（两条，都有铁证）

- **开发库被反复清空（持久性失败）**：MySQL `gold_analysis` 被一次
  `GOLDMIND_TEST_DATABASE_URL` 指向它的 pytest 在 `drop_all` 里删光，binlog
  （`LAPTOP-4576N368-bin.000248`，pos 134314155 → 134372602）里是完整的
  `use gold_analysis; DROP TABLE ...` 序列；只剩一张非模型的 `update_logs`，
  所有读库接口 500 —— 刷新永远不会好。
- **Yahoo Finance 对本机限流（间歇性失败）**：回填在 8 轮里对 11 个代码
  （`GC=F` / `DX-Y.NYB` / `^VIX` …）连续拿到
  `YFRateLimitError: Too Many Requests`，金价基准序列 `gold_close` 因此始终 0 行，
  量化页整片「缺少黄金价格序列」。
- **429 + 无重试（间歇性失败）**：看板每 10 秒对 stats / daily / correlation /
  dollar 各拉一次（≈30 次/分；首屏另有约 15 个区块请求、开发态 StrictMode ×2），
  逼近 60 次/分的上限；旧拦截器只重试「连响应都没拿到」的错误，429 / 5xx
  直接判失败 —— 整片红，过一会儿刷新又好。

### 2. 后端与数据（实测）

- `backend/init_db.py` 重建 10 张表后，`/health`、`/stats`、`/prices/daily`、
  `/prices/correlation?days=180`、`/dollar-realtime`、`/quant/{predictions,monitor,factors,accuracy}`、
  `/news` 全部 **200**（`gold_prices=453`、`dollar_index=458` 行）。
- `backfill_quant.py --apply --years 20` 跑完 8 轮（停止原因 `no_progress`）：
  累计新增 36,101 行 / 修订 0 行；剩余缺口全部来自 Yahoo 依赖序列。
- **本地行情兜底**：`sync.py` 在 Yahoo 失败且本地有行情时，用 `gold_prices` /
  `dollar_index` 补 `gold_close` / `dollar_index` 因子，落库来源标注
  「本地行情表…兜底」。实跑后 `gold_close` = **453 个观测**，
  `/quant/predictions` 的 1 / 5 / 20 / 60 / 250 日全部 `status=ok`（如 1 日
  `direction=up`、`target_price=4213.58`）；四层分解仍如实报
  「缺少回归量：VIX 波动率指数」（VIX 无本地来源，不编造）。
- 缺表/缺库 → **503 + 修复指引**：`ProgrammingError(1146)`、`OperationalError(1049)`、
  SQLite `no such table` 三种输入都命中；`Unknown column`（1054）仍走 500。
  起点自检 `_missing_metadata_tables()` 从 metadata 派生表名，不硬编码。

### 3. 前端（实测）

- 轮询 10s → **30s**；`document.hidden` 暂停、`visibilitychange` 恢复立即补一次；
  同一 URL 的在飞 GET 合并。空闲请求 = 4 个 URL / 30 秒 = **8 次/分**
  （旧口径约 30 次/分），且 StrictMode 双挂载不再翻倍。
- 请求重试：网络错误 / 超时 / 408 / 425 / 429 / 5xx（501 除外）指数退避
  （500ms 起、±25% 抖动、上限 10s、最多 3 次尝试）；429 优先 `Retry-After`，
  其次 body `retry_after`。`POST` 与 `GET ...?refresh=true` 永不重试（付费语义）。

### 5. 仍存在的诚实降级（不修）

- VIX / GVZ / 金银比 / 铜金比 / USDCNY 依赖 Yahoo，限流期间在页面上如实显示
  「不可用 + 原因」；不引入会改因子语义的替代来源。
- `fair_value` 四层分解需要 VIX，限流期间保持 `unavailable`；方向 / 区间 / 情景
  照常给出。
